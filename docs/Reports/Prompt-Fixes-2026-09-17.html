Scope of this report

This report describes the eight findings from the 15 September prompt review and their implementation in commit 174c9e6. It covers system prompts, tenant instructions, caller data, handoffs, text actions, policy storage, and evaluation checks.

Three Sol agents completed assigned parts of the work. The lead agent implemented evaluations and tenant guidance, reviewed the combined changes, and checked the commit. All used the Ponytail skill and the project’s RED / GREEN / REFACTOR process.

Read the status correctly. “Implemented” refers to the eight reviewed defects. Test and migration results below are the saved results from that work. The database and deployed app were not checked again for this report. The results do not certify every model response or establish production voice quality.

Architecture

How the prompt is now assembled

A published workflow supplies the agent configuration. A session selects a platform policy revision. The builders use these inputs to create the provider request.

  1. Platform rulesAuthority order and the selected saved guardrails.
  2. Specialist behaviorThe selected class template and its job instructions.
  3. Business configurationSerialized tenant identity and bounded instructions.
  4. Language and response contractResolved language settings and the required output format.
  5. Caller and runtime stateThe current request, recent conversation, actions, and tool results.
  6. External evidenceSource-labelled, bounded content treated as data.

The first four sections form the trusted prompt structure. Business configuration remains subordinate to platform rules. Caller state and external evidence do not define the action contract. Text providers also receive a native response schema for action turns.

This is a logical structure. Provider message formats differ. In particular, a named section in a system prompt is not a new provider role.

Fix 01 / Shared prompt construction

Apply platform rules to realtime calls

ImplementedOriginal severity: High

Original fault

Text calls used the saved platform guardrails and specialist template. The realtime builder did not use these fields. A staff policy change could therefore affect one call path and leave another unchanged.

Implemented behavior

Both prompt builders now use the selected platform policy. The realtime setup and handoff paths retain the guardrails and specialist template selected for the session.

Implementation details

  • The text and realtime builders share the authority rules and language formatter. Realtime keeps the extra instructions that it needs for voice and provider operations.
  • The realtime transport receives the session policy. The runtime also passes it during agent changes and call recovery.
  • OpenAI response instructions can replace session instructions for that response. The adapter now includes the full configured system prompt when it adds a response directive.
  • The initial greeting, transfer announcement, and continuation helpers build their prompt from the registered session. An empty prompt in a temporary adapter no longer removes the selected policy.

Illustrative scenario

A specialist template contains a unique refund rule. The rule is present when a text call starts, when a realtime call starts, and when the call moves to that specialist.

Verification

Shared builder tests passed 10/10. The adapter and runtime handoff/policy group passed 37/37. Tests use unique platform and specialist markers to inspect the generated provider requests. The premium phone media/handoff group passed 23/23.

Evidence limit. This verifies prompt construction and the tested call paths. It does not prove that every model will follow every instruction in every live call.

Fix 02 / Instruction and data boundaries

Keep handoff summaries in the data section

ImplementedOriginal severity: High

Original fault

The runtime read callerNeedSummary from a tool result and placed that text in response instructions. A summary derived from caller or model text could therefore enter a field used for commands.

Implemented behavior

Handoff summaries remain conversation or tool data. The runtime uses a fixed directive to continue the call. It does not turn the summary into a new instruction.

Implementation details

  • Continuation instructions are fixed application text. They no longer insert the caller summary or an untrusted agent name as a directive.
  • The target agent still receives the relevant transfer context through the supported conversation or tool-result path.
  • Shared rules permit the agent to use facts from the summary. They tell it to ignore commands embedded in that data.
  • OpenAI response overrides retain the selected platform prompt. Both the data boundary and the response-level policy are preserved during a handoff.

Illustrative scenario

A handoff summary says that an order is delayed, then contains a request to ignore the platform rules. The target can use the delayed-order fact. The extra request is not inserted as a continuation command.

Verification

Handoff and response-message tests check the generated payloads. The broader prompt/runtime regression passed 60/60. Live text checks also tested malicious instructions in tool data; the returned responses did not contain the test marker.

Evidence limit. The live text injection case is related evidence. It is not a live voice exploit test of the handoff path. Data labels and escaping reduce ambiguity; server permissions remain necessary.

Fix 03 / Evaluation quality

Make evaluations execute runtime behavior

ImplementedOriginal severity: High

Original fault

The main packet evaluation built an output from a fixture’s expected answers. It then scored that output against the same answers. A green result did not show that the runtime had produced the expected behavior.

Implemented behavior

The evaluation executor receives fixture inputs only. It runs production adapters, action parsing, tool checks, and route resolution. The scorer keeps the expected answers separately.

Implementation details

  • The offline executor uses the OpenAI text adapter, Gemini intent classifier, runtime tool executor, and packet update functions. Provider responses and tool services are controlled test doubles.
  • Tests use an incorrect route or an unassigned tool to check that the relevant score fails. The result is no longer copied from referenceOutputs.
  • The missing-input measure is named missingInputRejected. That name describes the server behavior observed by the offline test. It does not claim that a real model asked a question.
  • The default dataset is v2. A separate eval:prompts command calls OpenAI and Gemini with synthetic cases. The suite records provider, model, policy revision, and policy hash. Missing credentials cause a failure.

Illustrative scenario

The fixture expects the billing route. If the executed route result points elsewhere, the route score fails. The reference answer cannot make the produced result correct.

Verification

The runtime evaluation gate passed 5/5. Scorecard tests passed 12/12. The final live prompt suite passed 16/16 twice in succession. The suite covers eight cases for each of two text providers.

Evidence limit. The offline gate is a deterministic component/integration check with scripted provider output. The live gate has narrow pattern-based assertions. Neither is a complete quality assessment of all specialists, models, accents, or voice calls.

Fix 04 / Language behavior

Resolve language settings in one place

ImplementedOriginal severity: Medium

Original fault

The realtime prompt could allow a language switch while the OpenAI adapter added a default-language-only rule. Saved languagePrompts were retained in the workflow but were not read by the prompt builders.

Implemented behavior

One formatter resolves the current language, supported languages, switching rule, and saved language guidance. Both text and realtime prompts use it.

Implementation details

  • When switching is enabled, a supported selected language is used. Otherwise, the formatter uses the configured default language.
  • The prompt lists the supported languages. Saved guidance for the resolved language is included as business language guidance.
  • The adapter no longer adds a conflicting English-only instruction.
  • For a fixed-language call, even the explanation that another language is unsupported must use the configured language. Language labels include a readable name and code, such as English (en).

Illustrative scenario

A workflow supports English and French. With switching enabled, a clear request for French is allowed. With switching disabled, the agent answers in English and explains the limit in English.

Verification

Prompt tests cover the saved guidance and switching policy. Live checks cover allowed French and fixed English for both text providers. Expanded live tests exposed a fixed-language fault; the shared rule was corrected before the final two passing runs.

Evidence limit. This change resolves prompt policy. It does not expand the speech recognition or speech synthesis capabilities of a provider. The live text set does not qualify every supported language.

Fix 05 / Prompt structure and tenant authoring

Separate platform authority from tenant configuration

ImplementedOriginal severity: Medium

Original fault

Tenant names and free text were directly inserted beside platform instructions. The boundary was mainly a heading. Action-format instructions also appeared in the caller-turn message.

Implemented behavior

The system prompt states the authority order. Tenant identity and instructions are serialized as business configuration. The response contract is defined in the system prompt, and server checks still enforce permissions.

Implementation details

  • The system prompt starts with platform authority rules and saved guardrails, then specialist behavior. Business configuration has a distinct JSON section.
  • Business instructions apply only within platform rules and server permissions. Caller text, retrieved content, tool results, and summaries cannot change those rules.
  • The user-turn message contains caller text and runtime state. It no longer defines the JSON action contract.
  • Reusable-agent creation and workflow validation enforce a 12,000-character instruction limit. The workflow also checks each saved language prompt. The existing UI fields use the same limit.
  • The tenant forms show a compact example for purpose, process, tools, limits, handoff, and style. The work reused the existing forms and added no new setup screen.

Illustrative scenario

A tenant name contains a fake “Platform rules” heading. JSON serialization keeps it as a field value. A tenant instruction that conflicts with platform rules has no authority to change tool permissions.

Verification

Three failing tests first showed that oversized instructions were accepted. The implementation then passed the relevant API/workflow checks. The combined authoring/evaluation group passed 52 tests, and the two UI smoke flows passed 5/5. A live tenant-conflict case passed for both text providers.

Evidence limit. Business configuration still appears inside a section of the generated system prompt. JSON is not a separate provider role or a security guarantee. Tenant scope, tool grants, and approval decisions remain server responsibilities.

Fix 06 / Action reliability

Constrain action output with provider schemas

ImplementedOriginal severity: Medium

Original fault

Text providers were asked in prose to produce JSON. They did not receive an action response schema. The parser and server checks could reject bad output, but the request did little to prevent it.

Implemented behavior

OpenAI and Gemini receive a response schema built from the actions available for the turn. The existing parser and server permission checks remain after generation.

Implementation details

  • The schema permits respond, assigned tool calls, and configured handoff targets. It rejects extra fields in the defined action objects.
  • OpenAI receives response_format with json_schema and strict enabled. Gemini receives its JSON MIME type and responseSchema. The intent classifier also receives an output schema.
  • The provider response uses a root object with one action field. The allowed action variants sit inside that field. Review corrected an invalid root-level schema design.
  • Optional tool fields use nullable alternatives where required by the strict schema. The unwrap step removes only null placeholders added for optional fields. Valid null values, including nested values, are retained.
  • The provider wrapper is converted to the existing core action format. The runtime still checks assignments, arguments, approvals, and allowed routes before execution.

Illustrative scenario

For a turn with one order lookup tool, the schema permits that assigned tool ID. An unknown tool ID has no schema option and is still rejected by the runtime if it reaches the parser or executor.

Verification

The combined action, packet, workflow, provider, classifier, authoring, and evaluation regression passed 88/88. Focused schema checks cover optional-null handling. The live tool-ready case required the assigned order lookup with order ID 123.

Evidence limit. This implements structured JSON output for the existing action protocol. It does not replace the runtime with a new native function-calling design. A valid JSON object can still be the wrong business decision; authorization and result checks remain essential.

Fix 07 / Policy storage and release control

Store immutable policy revisions and pin each call

ImplementedOriginal severity: Medium

Original fault

Text providers could read a mutable file on each request. A call could change policy between turns. Version checking and saving were separate operations, so concurrent staff updates could overwrite each other.

Implemented behavior

Postgres stores immutable policy revisions. A database operation checks the expected version and writes the new revision atomically. Each session keeps its selected revision and hash.

Implementation details

  • runtime_prompt_policy_revisions stores policy JSON and its SHA-256 content hash. runtime_prompt_policy_current points to the current revision. runtime_prompt_policy_session_pins stores each session selection.
  • The initial startup imports the legacy file only if the database has no current policy. If no file exists, it stores the built-in default. Later starts use the stored revision.
  • Revision reads verify the hash and the exact stored content. They do not merge new defaults into old revisions.
  • Sandbox and standard phone calls reuse their selected policy. Premium dispatch snapshots carry the revision and hash. Recovery loads that exact policy; an unknown or inconsistent revision is not replaced with the latest one.
  • Staff can promote an older revision as a new revision through the audited promote endpoint. The request includes expectedVersion and reason. Existing sessions keep their original policy. Database triggers prevent revision and session-pin edits or deletion.

Illustrative scenario

Call A starts with revision 7. Staff save revision 8. Call A continues with revision 7; a new call selects revision 8. If two staff saves both expect revision 7, only one can write the next revision.

Verification

Policy repository/service/admin checks passed 20/20. Real isolated Postgres migration and dispatch-persistence checks passed 24/24. They cover atomic writes, immutable history, session pins, and exact revision recovery. Neon migration 0040 was later applied and verified.

Evidence limit. Migration 0040 creates the storage objects. Application startup selects or imports the initial policy. Durable prompt selection does not reconstruct every other part of a call after a restart. Old premium snapshots without revision/hash fields are rejected.

Fix 08 / Context and output limits

Bound the full request and keep recent action facts

ImplementedOriginal severity: Medium

Original fault

Packet compaction could remove the newest tool result first. Caller text and separate external context were outside that packet limit. The text providers did not set output token limits.

Implemented behavior

The full serialized text request has a conservative size guard and an output reserve. Packet compaction removes older tool results first. If the latest result must be shortened, the runtime keeps an explicit truncated result.

Implementation details

  • The full-request guard compares UTF-8 request bytes plus reserved output tokens with 32,768. Bytes are used as a conservative proxy for input tokens; this is not an exact tokenizer count.
  • Both text providers reserve up to 1,024 output tokens for an action response and 512 for a spoken response. Oversized requests fail before provider submission.
  • Separate untrusted context has an 8,000-character selection budget. Selection favors recent items. Exact copies of summaries or safe output already in the runtime context are omitted.
  • Packet compaction drops older tool results before the latest result. It preserves the latest status, summary, and safe output where the budget permits.
  • An oversized latest result retains a compact preview and an explicit truncation marker. The context tells the model not to repeat the action merely because details were omitted.

Illustrative scenario

A refund tool returns a large result. The next caller asks whether the refund finished. The compacted context retains the latest outcome, or an explicit shortened form, instead of removing it before older results.

Verification

Packet and provider tests are included in the 88-test regression. They check the request guard, output limits, duplicate handling, and latest-result retention. Review corrected an earlier byte-to-token calculation and an overly broad duplicate match.

Evidence limit. The 32,768 threshold is a fixed application guard, not a model-specific context calculation. It can reject a request that a model could accept. All details of a very large result cannot be retained. This does not prove unlimited conversation length or exactly-once tool execution.
